crew#722: enterprise-wide secrets rotation strategy. Founder 2026-08-31: "poorly designed enterprise-wide secrets rotation strategy, this will harm us badly if we let it slide." Twice in one week a vault write succeeded and the running program kept the old value (crew#506 CP4, crew#684); both were found by a person hitting a broken door. This wave ships the strategy (docs/policy/secrets-rotation.md, stages 1-5 with owners) and its two proving controls: a receipt row that goes red when any running pod is older than a Secret it consumes, and a daily canary drill that rotates a real vault entry and waits until the running pod answers with the new value. SLO 25 minutes, vault to pod, no hand.

Optimised: 21 steps -> 9, 13 round trips -> 4; cut: the per-file build-test loop (13 files fixed one by one) became one scripted sweep + one batched write wave, and the second local suite run was cut because CI runs the 413-file suite once on this PR (R58).

## Options considered
- kube-state-metrics + a PromQL rule: no metric relates a pod's start time to the write time of a Secret it references; building that join in PromQL means a recording rule per consumer — a list that rots. Rejected.
- A new freshness exporter: a second instrument nobody reads (LAW 28) and a script for a problem the graded receipt already owns (LAW 43). Rejected.
- Chosen: extend the estate's one graded instrument — the cluster-state receipt and its grader — plus a canary consumer on the estate's own reload standard, so the drill exercises exactly the road production secrets travel.
