# The dispatch boundary: an agent submits work and its turn ends

`dispatch_job` starts work detached and returns an id in **milliseconds**. There is no wait path in
it — no `status` argument, no `poll`, no blocking read. The agent's turn ends the moment it gets
the id, and it gets the outcome on a later turn or from the jobs page.

## Why the boundary is structural and not a rule

Measured **2026-09-13**: one session held **1,727,322 tokens across 7,594 messages** and re-sent its
whole history on every turn — **177,570 tokens per call, 56 calls in six minutes**, against one key
at **83% of its $15.00 budget**. Every one of those calls belonged to an open turn. A turn that
cannot stay open cannot spend.

An instruction not to block is a wish. **A tool with no wait path is a constraint**, and that is the
difference this makes.

## Install

```sh
bin/idp-dispatch-install
```

That symlinks `extensions/dispatch/` into `~/.pi/agent/extensions/`, which pi discovers at
`session_start`. **A session already running does not pick it up** — pi loads extensions once and
holds them in memory — so the tools appear in the next session.

## Use

Nothing for the founder. An agent calls the tool:

```
dispatch_job { task: "Run the ceiling suite", command: "pytest tests/test_request_ceiling.py -q" }
```

It returns in single-digit milliseconds with an id, a log path and a jobs-page URL.

## Expect

- the tool returns **immediately**; the turn ends
- output accumulates in `~/.estate/runs/<id>.log`
- `dispatch_result { id }` reads what is on disk and **never waits**
- the job appears on the jobs page, generated by `bin/idp-jobs-page` from
  `~/.estate/dispatch/jobs.jsonl`

## What it does not do

- **It cannot report when a job finishes.** That is the point. Use `dispatch_result` on a later
  turn, or read the page.
- **It does not replace `bash`.** Short reads are still direct; this is for work that outlives a
  turn.
- **It starts a local process and writes local files only.** It never touches the cluster, never
  mints a credential, and never merges anything.

## Defects found by running it, not by reading it

Both were found by dispatching a trivial job and reading its log — the same discipline that would
have caught the token leak two hours earlier:

1. **`run` ends in `nohup "$@"`**, so it executes its arguments directly with no `sh -c`. Passing
   the command as one string made nohup treat the whole command line as a binary name:
   `nohup: printf "...": No such file or directory`. Fixed by dispatching
   `bash -lc <command>` as one argv word.
2. **The ledger row is written even when the job fails to start.** A job that never ran still
   produced a clean-looking row. Only the log told the truth — so `dispatch_result` reads the log
   and reports the reason, and the page shows `no output recorded` rather than inventing a state.
