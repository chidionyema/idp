# Spec: every gate gets a demo

Founder, 2026-09-12: **"everything needs UI demo."**

There are 66 rules in `rules.yaml` and 5 recordings under `demos/`. The five were
hand-authored one at a time, which is why there are five. Hand-writing 61 more is not the
job and would rot: a tape is a claim about what a gate does, typed by hand, and nothing
checks it against the gate.

## What a gate demo is

One generated page per rule, in the portal, carrying **the gate's own real output** — not a
description of it, not a screenshot of a paragraph.

For each rule in `rules.yaml`:

1. **The claim** — `statement`, `law`, and the `ok` / `fail` lines, which already exist per row.
2. **The run** — the exact argv from `run`, so a reader can reproduce it.
3. **Refused** — run the rule's `must_fail` case, capture the real stdout/stderr and exit code.
4. **Permitted** — run the `must_pass` case, same.
5. **The verdict** — the two exit codes side by side, because a gate that refuses everything
   and a gate that refuses nothing are both proven here or neither is.

The page is generated by `bin/idp-gate-demo`, never edited by hand. A gate whose two cases do
not come out refuse/pass is a `BLIND` row on its own page, never a green one.

## Why generated and not a tape

A tape records a terminal; it cannot be checked. This runs the real gate against the real
fixture and writes the real bytes into the page. If a gate stops discriminating, its page
changes on the next render and says so — the demo cannot drift from the gate, which is the
one property a hand-typed demo never has.

## Files

- `bin/idp-gate-demo` — the generator: `--out docs/gates`, `--check`, `--only <id>`
- `docs/gates/<rule-id>.md` — 66 generated pages
- `docs/gates/index.md` — one row per gate: id, planes, law, refuse-exit, pass-exit, grade
- `mkdocs.yml` — the Gates section in the nav
- `tests/test_gate_demo.py` — the tests below

## Tests (failing until it is built)

1. `test_every_rule_gets_a_page` — one `docs/gates/<id>.md` per row in `rules.yaml`.
2. `test_the_page_carries_the_real_exit_codes` — running the rule's own two cases reproduces
   the exit codes printed on the page, byte for byte.
3. `test_a_refusing_gate_is_shown_refusing` — for a rule with a `refuse` case, the page
   contains that case's actual stderr, not the word "refuse" alone.
4. `test_check_is_idempotent` — `--check` exits 0 when the pages match the registry and 1 when
   one is edited by hand. Two runs over one registry are byte-identical.
5. `test_blind_when_a_case_cannot_run` — a rule whose gate binary is absent gets a `BLIND`
   page naming the missing binary, never a page that reads as a pass.
6. `test_the_index_lists_every_gate` — the index has one row per rule and every row links a
   page that exists.
7. `test_pages_are_in_the_nav` — every generated page is reachable from `mkdocs.yml`.
