One cause, five symptoms

Attributed with counters, not narrative
  1. The Colima VM has 4 CPUs, 8 GiB and no swap at all. Right now 234 MiB is free and 6,046 MiB is page cache.
  2. kswapd0, the kernel's reclaim daemon, is pinned at 94% of a core. With no swap it can only evict page cache, and it is not keeping up. System time is 56%; idle is 0.0%.
  3. Containers therefore accept connections and never get scheduled to answer them. This is why a container can report healthy and return HTTP 000 — the healthcheck proves the process is alive, never that it can do work.
  4. Healthchecks is one of those containers. It is what placement-audit reads. So the audit goes Blind on 35 of 45 estate jobs — it reports UNKNOWN rather than inventing a verdict, which is correct behaviour and still a hole.
  5. Langfuse cannot come up, so observability stays unproven and three of the six improvements cannot be demonstrated. But see below — the VM was only half of that one.

Found while writing this page: a second cause, and it was mine

I had been attributing Langfuse entirely to the VM. It was also crash-looping on a syntax error in a config file I wrote. clickhouse-low-memory.xml contained a double hyphen inside an XML comment, which is illegal, so ClickHouse refused the whole file and died on boot in a loop:

SAXParseException: Invalid token in
'/etc/clickhouse-server/config.d/low-memory.xml', line 12 column 55

Because langfuse-web and langfuse-worker both wait on ClickHouse being healthy, neither was ever started. docker ps -a listed them as Created rather than Exited — which reads like "not reached yet", not like a fault. That is why three hours of looking at the VM never found it.

Fixed and pushed. ClickHouse now stays up instead of restarting. Writing the fix introduced a second double hyphen, inside the sentence naming the validator, because the validator's flag is spelled with two hyphens — so the check now lives in bin/langfuse-up instead of in a comment, proved both ways: the real file exits 0, the same file with the hyphen put back exits 1.

A correction, and the instrument that caused it

I told you on crew #85 that this was CPU pressure and "memory is NOT the constraint — 5,987 MB available." That is withdrawn. MemAvailable is an estimate that assumes reclaiming page cache is cheap; kswapd burning 94% of a core is the proof that it is not.

Two hypotheses died on the way, both killed by counters rather than argument: a transparent-hugepage compaction storm (compact_stall 0, AnonHugePages 0) and disk wait (%Cpu wa 0.0). A peer session's disk-wait theory is wrong for the same reason.

The instrument lied in a way worth remembering. top -b -n1 reports %CPU as an average over the process's whole lifetime, not the moment. Its first frame blamed kcompactd at 60%; a real five-second sample showed kcompactd using zero ticks. Only the second frame of top -b -n2 tells you what is happening now. That is the fifth instrument this week that answered a question it was never asked.

Before any of that: write the standard

The recommendation

Certification cannot be scored against a page that has no pass condition. The smallest fix that makes "100% certified" a real sentence is one gate — bin/idp-certify — that runs the six gates above plus the acceptance criteria as commands, prints one line per capability, and exits non-zero if any is unproven or unreadable. Three states, not two: Pass Fail Blind. A guard that loses its evidence must say so rather than return a verdict — that defect has now been found and fixed three separate times this week, in rego, in bash, and in a numeric comparison.

Then the answer to your question stops being a document I wrote and becomes a command you can run from your phone.
