# 0013. Customer identity is Keycloak, the realm is code, and a reconciler owns it

- Status: PROPOSED 2026-08-31. Only the founder moves a thing to live, so this
  records the choice and the first slice built against it; it does not claim anything runs.
- Date: 2026-08-31
- Deciders: founder
- Extends [the front-door decision](0007-the-front-door-is-federated-login-with-no-local-password.md),
  and does not replace it. That one is the door **staff** come through, and it stays exactly as it
  is. This is the door **customers** come through.
- Affects: the storefront's sign-in, and the one account in its database.

## The problem, measured

The storefront carries its own sign-in code and its own account table inside `/data/store.db`,
the single file that is also the whole shop: 202 packs, 3 orders, 41,035 analytics rows, 23
tables. The account count in it is **one**. The founder, 2026-08-30, on reading that count:
"the identity job is now tiny. One user account. Nothing to migrate."

So the reason to act is not migration cost. It is that a shop with its own sign-in code owns
password storage, reset flows, session handling and lock-out, and a buyer's engineer will open
exactly those four files first. The front-door decision already settled the principle for staff — "the estate
never holds a password for a person" — and the shop is the one surface still outside it.

## The decision

**Customer identity is Keycloak. One realm, `shop`. The realm is a file in this repository, and a
reconciler applies that file on every run. The storefront keeps no sign-in code and no account
table.**

Five parts, and each answers one thing the founder named.

**1. The realm is code, and it is a subset on purpose.**
`platform/customer-identity/realm/shop.yaml` holds the 27 settings and 2 applications this estate
has an opinion about. A read-back of a live realm carries several hundred keys; the rest are the
vendor's defaults, and checking them in would mean re-checking them on every upgrade. No hostname
is typed into the file, because a file never names where a machine lives; they arrive through the
reconciler's own substitution.

**2. The reconciler is keycloak-config-cli, and it is named because import is not a reconciler.**
The founder, 2026-08-30, named the flaw in his own words: `alm import is create-only, not
reconcile`. That is exactly right about
the Keycloak Operator's realm import, which is why the Operator is not the answer to this half.
keycloak-config-cli (Apache-2.0, adorsys) describes itself as `declarative, idempotent
configuration for Keycloak via the Admin API - version-controlled and CI/CD-ready`. Safe to run
again is the whole reason it is here: run it twice on an edited realm and the edit is gone. It runs as a
Job on every change to the file, not on a timer, so the file is the only way in.

**3. The first administrator is the one thing that cannot be declarative, and it is bounded.**
Keycloak's first administrator has to exist before anything can talk to the administration
interface, so it cannot come from a file the administration interface is needed to apply. The
sequence: the server starts with a bootstrap administrator whose password is generated by the
pipeline into the estate vault and never printed; the reconciler runs with it once; the
reconciler creates its own service account; the bootstrap administrator is then disabled in the
same run. Nobody is ever sent a password, which is the whole point of the front-door decision.

**4. Drift is measured, not assumed.**
The founder: `the realm's live state must be diffable against git in CI`. `bin/idp-realm-diff`
reads the realm back and grades every key git declares against it. Every key git declares must
match; a key git is silent about is not drift. It exits 0 for a match, 1 with each difference
named, and 2 — never 0 — when it could not read anything. A credential is compared by presence
and never by value, so no secret reaches a build log.

**5. Break-glass includes reading, not just fixing.**
Two paths, and the read-only one is the one that gets used. A realm role that can read every
object in `shop` and change none is what an on-call session gets for diagnosis; the write path is
the bootstrap administrator, re-enabled by a pipeline run that says who asked and why, and
disabled again by the same run. A diagnosis that needs write access is a design fault, not an
emergency.

## Why not the alternatives

- **Keep the storefront's own sign-in.** It is the thing being removed. Password storage, reset
  and lock-out are four files nobody reviews, in the product a buyer is buying.
- **Point customers at the staff door.** The directory behind the front-door decision is an
  administration directory with a grant table of named addresses. It is the right shape for six
  staff and the wrong shape for a shop that must let a stranger register.
- **The Keycloak Operator's realm import instead of a reconciler.** Create-only. The founder's own
  objection, and it is correct.
- **Terraform's Keycloak provider instead.** It does apply the declared state, and it was the first
  suggestion this estate's router lane produced. It also puts the truth about a realm in a
  Terraform state file rather than in the realm file, which is a second place to disagree with
  git; and it makes every sign-in setting a plan-and-apply against a live server rather than a
  file a reviewer can read. The realm file is the artefact we want reviewed.
- **A second identity service for the shop, separate from everything else.** That is the stitching
  the headline forbids. Keycloak is the estate's one customer-facing identity layer; if a second
  product needs customers, it gets a second realm on this server, never a second server.

## Consequences

- The register gains a `customer-identity` feature, default **off**. Nothing runs until the
  founder's word flips it, in its own pull request, next to the storefront change that removes
  the old sign-in code.
- Sizing, from the vendor's page and not from memory: `1250 MB of RAM` for a pod including caches
  and 10,000 cached sessions; Keycloak `allocates 70% of the memory limit for heap-based memory`
  plus `approximately 300 MB of non-heap-based memory`; `For each 15 password-based user logins
  per second, allocate 1 vCPU`, with `150% extra head-room`. One shop with one account needs the
  memory floor and none of the processor guidance.
- The database is **not** a seventh Postgres. The register already carries the consolidation
  (`shared: postgres, instances_today: 6, target: 1`); Keycloak takes a database on that one. If
  the shared instance does not exist when this feature is switched on, that is what blocks the
  switch, and adding another copy is not the way past it.
- The one existing account moves as rows, not as a file. `/data/store.db` is the whole shop and is
  not deleted, renamed or replaced by any part of this.

## What this does not decide

The sign-in screen the customer sees, and whether the shop offers a federated provider next to
email. Both are the next slice, and neither changes anything above.
