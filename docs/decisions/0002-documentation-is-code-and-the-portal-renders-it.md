# 0002. Documentation is code, and the portal renders it

- Status: PROPOSED
- Date: 2026-08-24
- Deciders: founder (only the founder accepts, R16)
- Supersedes: nothing. This is the first documentation decision the estate has recorded.

## Context

The founder asked two questions in one breath: do we have a documentation strategy, and are we
adopting standards. The honest answer to the first is no, and it is measurable.

Measured on this machine on 2026-08-24:

| What | Count | How |
|---|---|---|
| Markdown files under `~/dev/code` | 2,497 | `find -name '*.md' \| wc -l` |
| Of those, not in any git repo | 2,034 | `git ls-files '*.md'` vs `find`, per repo |
| `mkdocs.yml` files | 0 | `find -name mkdocs.yml` |
| Decision records in the estate | 13 | `adr-sources-guard.py --sweep ~/dev/code` |
| Of those, citing a single source | 0 | same command |
| `catalog-info.yaml` entities | 3 | `find -name catalog-info.yaml` |
| Entities declaring `dependsOn` | 0 | `grep -rl dependsOn --include=catalog-info.yaml` |
| Entities declaring `providesApis` | 0 | same |
| Architecture diagrams of the estate | 0 | no `.dsl`, `.puml`, `.drawio` anywhere |

Two of those rows are the whole problem. We run Backstage with TechDocs configured
(`builder: local`, `generator: docker`, `publisher: local` in `backstage/app-config.yaml:158`)
and there is no MkDocs site anywhere for it to render. And the catalog has three entities with
zero relationships, so the dependency graph the portal is famous for draws nothing.

A portal renders what it is given. It does not discover an estate. Standing one up and watching
the UI load is not the deliverable, and calling that live is the thing R16 exists to stop.

## Decision

Four standards, each doing one job, each already the mainstream choice with tooling we run.

**1. Structure: Diátaxis.** Four directories, `docs/tutorials/`, `docs/how-to/`,
`docs/reference/`, `docs/explanation/`. A page that fits none of the four does not belong in
`docs/`. Adopted by Canonical across its documentation and by the Python documentation
community, which is the adoption bar we want: not a blog post, an organisation that had to
migrate a large corpus and published how it went.

**2. Decisions: MADR, in `docs/decisions/NNNN-title.md`.** MADR is the ADR template maintained
under the `adr` GitHub organisation, which is also where the original Nygard format lives. Every
row of `crew/docs/STANDARDS.md` cites the ADR that chose it. This file is number two; ADR 0001
chose Gateway API.

**3. Delivery: docs-as-code through Backstage TechDocs.** Docs live in the repo they describe,
change through pull requests, and are rendered by the portal we already run. Backstage's own
guidance is `backstage.io/techdocs-ref: dir:.` on each documented entity, for exactly the reason
we want it: the documentation is authored beside the source it describes. No wiki, no Notion, no
second doc site.

**4. Architecture diagrams: C4, modelled in Structurizr DSL, rendered to Mermaid.**
`architecture/workspace.dsl` is the model; every diagram is a view of it. `architecture/render`
runs the model through the `structurizr/structurizr` container and writes
`docs/architecture/index.md` with the views as Mermaid fences, which GitHub and TechDocs both
render with nothing installed. The model is committed, the render is committed, and the render is
regenerable, so a diagram cannot quietly disagree with the model.

Raw Mermaid was rejected as the source of truth. Mermaid is the most widely rendered
diagram-as-code syntax, which is why it is the OUTPUT format, but hand-written Mermaid is four
independent pictures that drift apart. Structurizr separates model from view: adding a view later
does not mean redrawing the existing ones.

**And the catalog gets the relationships.** `dependsOn`, `providesApis` and `system` are what turn
three entities into a graph. They are generated by `bin/catalog-gen` from the LAW 39 inventory,
never hand-edited, so the fix is in the generator.

## What we are NOT adopting, and why

**AGENTS.md is not a documentation standard, and we already have it.** It is a community
convention, plain Markdown, no schema, no required fields, no versioned specification. That is a
feature for what it does — telling an agent how to work in a repo — and it is read natively by
Claude Code, Codex CLI, Cursor, Copilot, Gemini CLI and others, on the order of 60,000
repositories. `~/AGENTS.md` is our copy and it stays. It is instructions to agents. It is not how
the estate documents itself, and no part of this decision changes it.

**AAIF changes nothing here yet.** The Agentic AI Foundation was founded in March 2026 by
Anthropic, OpenAI, Google, AWS, Microsoft and Salesforce, and it governs agent-facing standards
(MCP and the agent-file conventions). It publishes nothing about how a platform documents itself.
Adopting it is not an option that exists for this question.

**No second standards document.** `crew/docs/STANDARDS.md` is the only one. This ADR becomes a row
in it.

## Consequences

Good: TechDocs stops being a tab with nothing behind it. The catalog draws a real graph, which is
the first screen a buyer's engineer opens. Every decision after this one carries the evidence it
was made from, enforced rather than intended.

Costs: 2,034 untracked markdown files have to be classified as ours or vendor, and 2,033 of them
are one directory (`hermes-v2/hermes-agent`). Thirteen existing decision records cite nothing and
have to be back-filled or marked historical. Six repos each need a `mkdocs.yml`.

Enforced by `~/.claude/scripts/adr-sources-guard.py`: a decision record with no `## Sources`
heading and fewer than two distinct source URLs is refused. Two, because one source is usually a
vendor's own page about itself. Proved both ways in one run (`--selftest`), and `--sweep` prints
the count of existing records that fail rather than asserting there are none.
