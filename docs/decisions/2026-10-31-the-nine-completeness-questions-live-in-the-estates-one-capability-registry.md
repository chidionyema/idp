# 2026-10-31 -- the nine completeness questions live in the estate's one capability registry

**Status:** accepted
**Claim:** chidionyema/idp#7671
**Agent:** pi

## What arrived

An outside proposal, `catalog-gate-v0` (a three-file archive: a README, an extractor and
its tests), that asks nine questions of every capability in a catalogue and holds a
ratchet baseline of the answers:

1. owner -- who owns this?
2. description -- what does it do?
3. status -- is it running?
4. last verified -- when was it last proven?
5. dependencies -- what does it need?
6. interfaces -- what does it take and return?
7. known issues -- what is broken about it?
8. mirrors -- does the same thing exist elsewhere?
9. metrics -- how is it measured?

Its gate reads `catalog/catalog-info.yaml`.

## Why it was not landed as it arrived

`catalog/catalog-info.yaml` is **gitignored and generated** (`.gitignore:11`); it is built
from a machine-local inventory and is not committed. A merge-point gate whose input does
not exist at the merge point is not a gate: it is a script that works on the laptop that
wrote it. Measured, not assumed:

```
$ python3 catalog_completeness.py extract --root . --out /tmp/cg-facts.json
593 entities extracted
$ python3 catalog_completeness.py completeness --root .
error: FileNotFoundError [Errno 2] No such file or directory: 'catalog/catalog-info.yaml'
```

The estate also already keeps **one** capability catalogue and **one** gate for it
(law 6: one of each layer, a second copy is stitching and gets deleted):

- `catalog/estate-capability-registry.json` -- the committed, machine-generated witness
  (1029 records), a pure function of the tree, regenerated by
  `.github/workflows/registry-snapshot.yml` and checked for drift by `bin/registry-gate`;
- `bin/capability-index` -- the one writer and query surface;
- `bin/registry-gate` -- the one gate (I-1..I-6, schema, coverage, freshness, drift,
  receipt integrity), run at the merge point by `bin/idp-ci` rung 8f.

Seven of the nine questions were already answered by the existing registry -- owner,
description, status/health, last-verified/proof, dependencies, interfaces, metrics. Two
were genuinely missing: **known issues** and **mirrors**. A third field, `consumers`, was
present on all 1029 records and empty on all of them.

The proposal's extractor also substantially duplicated extraction `bin/capability-index`
already performs (AST-based script and import analysis), so it was not carried over.

## What was done instead

The requirement was mapped onto the existing store, in the existing gate.

**Two new answers, taken only from the tree:**

- `known_issues` -- the faults a capability's own file declares, matched by a
  comment-anchored marker (`#`, `//`, `*`, `--`, `;` followed by
  `KNOWN[- ]ISSUE|FIXME|TODO|XXX|HACK`). Anchoring matters: an earlier free-text rule
  reported 19 "issues" that were variables and regex source; the anchored rule reports
  **1** -- `platform/warden/warden.py:76` ("This requires tracking when the key was last
  rotated/created").
- `mirrors` -- the other places the same capability **name** is declared, matched by stem
  over `bin/`, `platform/`, `mcp/`, `.github/` and `clusters/`. By name, not by raw
  basename: basename matching reported generic noise (`main.go`, `deployment.yaml`), the
  stem index reports **64** genuine duplicate declarations -- `mcp/agentgateway` in three
  places, `estate-inventory` as an intent, a workflow and a libexec.

**One new answer, derived from what the registry already knows:**

- `consumers` -- the inverse of the dependency edges, so "who uses this" is answerable.
  This is R-62's "unconsumed capability" test, which was previously unanswerable.

**The gate.** `bin/registry-gate` gained `check_completeness()` and
`completeness_falsifiers()`. The check runs on the **committed witness** (the merge-point
truth; the drift check above has already proved it equals a fresh generation of the tree),
and refuses on two different things:

- a **hole** -- a record that has no value for a question and declares no unknown. The
  estate may be blind; it may not be silent. An unknown is acceptable only when the
  record's `blind` list names that field.
- a **regression** -- measured coverage below the committed floor. "Measured" is a value
  or a measured negative ("no known issue", "no mirror"): a question the estate actually
  measured. An explicit unknown is honest but is not a measurement, so it does not count
  toward the floor. The comparison is a ratio compared by cross-multiplication
  (`current_measured * floor_total < floor_measured * current_total`), so deleting a
  capability does not lower the floor and adding one that answers less does. A catalogue
  that goes empty is refused in its own right: no records is not a clean bill of health.

**"Measured" is the number the ratchet holds, and the answer is in the order.** A real
value first; then a **declared unknown** (the estate says it cannot see this); then a
**measured negative** ("no known issue", "no mirror"); then a **hole** (silence). A
declared unknown beats a measured negative, because a record that says "I cannot see
this" must not also claim "there is nothing there". The floor holds the *measured*
fraction: the questions the estate actually measured, for the records it has.

The ratchet deliberately does **not** hold the number of issues found. When the marker
rule was tightened, the estate's known issues fell from 19 to 1 -- because 18 of them were
false positives, and refusing that change would have refused the truth. Completeness is
"every record answers"; knowledge gained is a different measure, and a ratchet that
punishes a true correction is a gate that fails the work it should protect.

**`health.state == "declared"` is an explicit unknown**, not a status value: only
`operating`, `degraded` and `frozen` count toward the ratchet.

**The floor is committed and machine-generated**:
`catalog/estate-completeness-baseline.json`, written by
`bin/capability-index completeness --write-baseline`, and re-baselined only by an
explicit act.

## A second class, closed in the same change: the witness carried the founder's home path

The witness's own contract says it: "no timestamps, no absolute paths, no machine state".
The intent `founder.decision` ships three parameter defaults like
`/Users/roseonyema/Documents/code/idp`, and the snapshot copied them in -- so the
committed witness carried the founder's user name onto every other machine, and the
estate's own test (`test_the_committed_snapshot_has_no_machine_state`) was red for that
reason:

```
E  assert '/Users/' not in '{\n  "schem... }\n  ]\n}\n'
E    '/Users/' is contained here:
E    ... "default": "/Users/roseonyema/Documents/code/idp" ...
```

The defect is the class, not the one intent: **any** source file can carry a home path
into the witness. The fix belongs in the writer, not in the intent, because the writer
owes the contract and the intent is not the only source. `bin/capability-index` now folds
any home directory to `~` -- `/Users/<name>/` and `/home/<name>/` -- before the witness is
written. The rule is machine-independent on purpose: the founder's
`/Users/roseonyema/Documents/code/idp` and a runner's `/home/runner/work/idp` fold to the
same `~/...`, so every machine generates the same bytes. The intent file itself is
unchanged: the runtime still gets the absolute path it needs; only the witness is
normalised.

The falsifier is in `tests/test_registry_completeness.py`
(`test_the_witness_carries_no_home_path`): the committed witness must contain no
`/Users/`, no `/home/` and no `str(Path.home())`, and the folding rule is proven on a
known-bad sample.

## The falsifiers (a gate that cannot fail is not a gate)

`bin/registry-gate` carries the cases that must trip it, and
`tests/test_registry_completeness.py` is the same proof as a test suite:

| Case | Must be refused |
|---|---|
| a record with no value and no declared unknown | yes -- a hole, named |
| a record whose measured coverage is below the committed floor | yes -- a regression, named |
| a declared unknown (`blind` names the field) | no -- blindness is allowed, silence is not |
| a measured "none" (the field was measured, the answer is empty) | no -- it is a measurement |
| no committed baseline | yes -- "no verdict" is said, not invented |
| an empty catalogue | yes -- no records is not a clean bill of health |

The gate proves it can fail on its own terms: `completeness_falsifiers()` builds a
record with a hole and a floor the tree cannot meet, and refuses both, on every run of
the gate.

## Trade-offs, stated

- **Cost at write time.** The enrichment reads the tree once more per context. Measured
  on this machine's disk (96% full, heavy load): `bin/capability-index emit --write`
  1m44s, against 7.4s on an idle disk. The gate already scans the tree twice (census and
  drift); the enrichment shares the census's context cache, so it is paid once, not
  twice.
- **Determinism.** The answers come from the repository only: no timestamps, no absolute
  paths, no machine state. Two generations of the witness are byte-identical, and a home
  path that reaches the tree is folded to `~` by the writer before it can reach the
  witness.
- **False negatives are preferred to false positives.** A marker that does not look like a
  marker is not a known issue. The alternative -- the 19 noisy records -- would have made
  the catalogue a liar, which is worse than incomplete.
- **The floor can be re-baselined, and that is the soft spot.** A re-baseline is an
  explicit act with a diff in the PR; it cannot happen silently.

## What was deliberately not done

- A second Backstage-style catalogue gate (its input does not exist at the merge point).
- A second extractor (`bin/capability-index` already extracts the code).
- A second store (the registry is the one store; the floor is a file beside it).
- Populating `status`, `last_verified` or `metrics` with invented values. The unknowns
  stay unknown and machine-visible.
