# Onboarding — the cross-node drill

**Door (from the UI):** Backstage → Estate → **Drills**. The hourly `verify-drill` run carries a
row named `cross-node`; open it to see the last verdict. A red row pages through the same lane as
every other drill row. You never need a terminal to read this.

## What you are being handed

Two small canary pods, one on each worker node, in the namespace `cross-node-drill`. Every 15
seconds each one resolves its peers through the headless Service and opens a TCP connection to
the pod on the other node, sending a short marker first. The peer logs the address the connection
arrived from. That is all they do.

`bin/idp-cross-node-drill` reads those logs — it never execs into a pod and needs no write grant
on the cluster, so it runs under the ordinary read-only drill identity. It grades two things for
each ordered pair of nodes: whether the connections succeeded, and whether each arrived wearing
the sending pod's address rather than a node address.

## Where each piece lives

| Piece | Path |
|---|---|
| Namespace, with the restricted pod-security labels | `platform/cross-node-drill/namespace.yaml` |
| The two canaries and their headless Service | `platform/cross-node-drill/deployment.yaml` |
| The fence around the namespace | `platform/ns-fences/network/cross-node-drill.yaml` (generated) |
| The Flux row that owns all of it | `clusters/oke/platform.yaml`, Kustomization `cross-node-drill` |
| The reader and its verdict | `bin/idp-cross-node-drill` |
| The hourly row | `bin/idp-verify-drill`, row `cross-node` |

The fence is generated by `bin/idp-ns-fence-gen`, not written by hand, and it is deliberately the
ordinary default-deny fence every namespace gets: default-deny both ways, a DNS exception, and an
allowance for traffic inside the namespace. That last allowance is a pod selector, which is
precisely what a masquerading node address fails to match — so the drill lives inside the same
kind of fence that the outage silently broke, and is graded by it.

## Reading a verdict

- `ok` on all four checks — pods on either node reach each other and arrive as themselves.
- `FAIL reach` — packets are not completing between the nodes. This is the outage shape.
- `FAIL source` — packets arrive, but wearing an address that is not the sending pod's. Something
  on the path is masquerading pod traffic; look for a leftover chain in the nodes' `nat` table.
- `BLIND` (exit 2) — the drill could not measure. Both canaries were not scheduled one per node,
  or their logs could not be read. This is never treated as a pass.

## What to do when it goes red

The drill names the addresses on both sides. Take the node that is failing to be reached and read
the ordering of its `nat` `POSTROUTING` chain: the estate's masquerade belongs to Calico and is
correctly scoped to exclude pod-to-pod traffic, so any other chain jumped to ahead of it is the
suspect. Removing a stale chain is a cluster change and needs the founder's own words before it
runs.

## Changing it

Edit the manifests under `platform/cross-node-drill/` and open a pull request; Flux applies them.
Do not edit the generated fence — change `platform/ns-fences/allowances.yaml` and re-run the
generator. If a third node joins the estate, raise the Deployment's replica count to match; the
anti-affinity does the placement and the drill grades every ordered pair it finds.
