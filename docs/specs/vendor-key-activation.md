# Spec: a vendor API key is activated from the portal, proved before it is stored, and watched afterwards

Status: SPECIFIED 2026-09-04. Written to be built without asking a further question (R29).
Implementer: the `deepseek` lane on the estate router.
Grounding: `docs/reference/identity-and-secrets-review.md`, measured 2026-09-04 14:22Z.

## The outcome

A person whose vendor key has expired opens the portal they already sign in to, chooses the
vendor, pastes the new key once into a field, and clicks Activate. Within seconds the page tells
them the vendor accepted the key, or it tells them exactly what the vendor said and stores
nothing. They never see a console of ours, never touch a repository secret, never open a terminal,
and are never asked again until the key actually stops working — at which point the estate tells
them before their traffic notices.

The founder is enterprise client zero (LAW 54): he is the first person this is built for, and the
surface he gets is the surface a customer gets.

## The four decisions this build makes, and the alternatives rejected

**1. The value is written to Bitwarden Secrets Manager, not to the OCI vault.** Decision 0017
already splits the two stores by provenance: machine-born secrets live in the estate's OCI vault,
human-born secrets live in Bitwarden. A vendor API key that a person created at the vendor's own
console is human-born by that definition. `ClusterSecretStore/human-vault` is live, Ready and
validated, and has never had one secret put through it; this build is what it was approved for.

Rejected: giving the Backstage backend write access to the OCI vault. The portal is the estate's
widest-reachable authenticated surface, and vault-write from it is a blast radius nobody would
sign off in diligence.

Rejected: a new `secret-provider` service. It would need its own door, its own identity, its own
policy exception and its own catalogue row to do what an HTTP call from a pod that already exists
does in twenty lines. The platform already solves storage (Bitwarden), delivery (External Secrets
Operator) and login (the front door); a service in the middle of those three adds a layer to
operate and nothing a buyer would pay for.

**2. The key is proved against the vendor before it is stored, and a failure stores nothing.**
`platform/vendors/consoles.yaml` already carries, for every one of the eleven vendors, a `shape:`
regular expression and a `verify:` block naming the exact HTTP call that proves a key. That file
is the single source of truth for this build; no vendor detail is hard-coded anywhere else.

**3. The admin surface is a Backstage Scaffolder template, not a new application.** ADR 0008: every
founder action is a portal button. It rides the front door that already exists, so this build adds
no login, no session, no user record and no second SSO.

**4. The button does not go through GitHub Actions.** Every founder-action template today is
generated by `bin/idp-portal-buttons` from a workflow and fires `github:actions:dispatch`. A
`workflow_dispatch` input is recorded in the run and readable in the Actions UI, so that road
cannot carry a secret value. This template is hand-written, lives outside the generator's
directory, and is handled by a Scaffolder action inside the portal's own backend.

## Part A — the Backstage action

Create a backend module package at `backstage/plugins/scaffolder-backend-module-vendor-key/`,
following the layout of the existing `backstage/plugins/catalog-backend-module-dagster-entity-provider`
(same `package.json` shape, same TypeScript config, same `src/index.ts` default export of a
`createBackendModule`). Register it in `backstage/packages/backend/src/index.ts` beside the other
module imports.

It registers one action, `estate:vendor-key:activate`.

**Input schema**

| field | type | notes |
|---|---|---|
| `vendor` | string, required | must be a top-level key of `consoles.yaml` whose `kind` is `secret` |
| `key` | string, required | the secret value; the template marks it `ui:field: Secret` |

**Behaviour, in order. Any step that fails stops the action, returns the reason, and writes
nothing anywhere.**

1. Load the vendor registry. The action reads it over HTTP from
   `https://raw.githubusercontent.com/chidionyema/idp/main/platform/vendors/consoles.yaml`, the
   same way the infra-crew container fetches the law files, so the portal image is not rebuilt
   when a vendor is added. Cache it in memory for five minutes.
2. Reject an unknown vendor, or one whose `kind` is not `secret`, naming the vendors that are
   valid.
3. Trim surrounding whitespace from the key. If the vendor row has a `shape:`, refuse a value
   that does not match it, and say what shape was expected — never echo the value.
4. Run the vendor's own `verify:` call exactly as the row specifies: its `method`, its `url`, and
   its `headers` with `{key}` replaced by the value. Timeout 15 seconds, no retry.
   A 2xx is the only pass. On anything else, return the vendor's status code and the first 200
   characters of its response body, and store nothing. This is the fail-closed requirement.
5. Write the value to Bitwarden Secrets Manager, one secret per vendor target field, using the
   REST API at `https://api.bitwarden.com` with the machine-account token described in Part C.
   The secret's key is the `field` of each entry in the row's `targets:` list — for example
   `DEEPSEEK_API_KEY`. Create it if absent, update it in place if present. The project is the
   `BITWARDEN_PROJECT_ID` already in `clusters/oke/estate-config.yaml`.
6. Return a result naming the vendor, the number of targets written, and the verify call's status
   code. The value itself never appears in the return, in a log line, in an error message or in
   the Scaffolder task record.

**Logging.** The action logs the vendor name, the verify URL, the status code and the target field
names. It must never log the key, and it must never log a header it constructed from the key.

## Part B — the template

`backstage/templates/founder-actions/activate-vendor-key/template.yaml`, hand-written, carrying a
first-line comment saying it is not generated (the generator's files all begin with `# GENERATED
by bin/idp-portal-buttons`, and a check reads that line).

```yaml
apiVersion: scaffolder.backstage.io/v1beta3
kind: Template
metadata:
  name: activate-vendor-key
  title: Activate a vendor API key
  description: Paste a new key once. The vendor is asked to confirm it before anything is stored.
  tags: [founder-action, estate, secrets]
spec:
  owner: group:default/platform
  type: founder-action
  parameters:
    - title: The key
      required: [vendor, key]
      properties:
        vendor:
          title: Which vendor
          type: string
          description: The lane whose key stopped working.
        key:
          title: The new key
          type: string
          ui:field: Secret
          description: Pasted once. It is sent to the vendor to be confirmed, then stored; it is never written to a log, a repository or this page's history.
  steps:
    - id: activate
      name: Confirm with the vendor and store
      action: estate:vendor-key:activate
      input:
        vendor: ${{ parameters.vendor }}
        key: ${{ secrets.key }}
  output:
    text:
      - title: Result
        content: ${{ steps.activate.output.summary }}
```

The `vendor` field is a plain string with a static enum generated into the template by
`bin/idp-portal-buttons` in a later pass; for this build it is typed, and an unknown value is
refused by the action with the valid list in the message.

`backstage/app-config.yaml` already restricts which templates the scaffolder offers (see the
comment at line 264). Add this template's location there.

## Part C — the credential the portal uses

The estate already holds one Bitwarden machine-account token, seeded once, in the estate vault and
delivered to `external-secrets/bitwarden-access-token` for the store to read. The portal uses that
same machine account — no second credential is created and nobody pastes anything.

Add `platform/backstage/overlays/oke/bitwarden-external-secret.yaml`: an ExternalSecret in the
`backstage` namespace, `secretStoreRef` `estate-vault`, pulling the same vault entry into a Secret
named `bitwarden-portal-token`, mounted into the Backstage pod as a file (never an environment
variable — the cluster policy `secrets-not-from-env-vars` refuses `secretKeyRef` env outright).
The action reads the file at start and on each invocation, so a rotation lands without a restart.

The machine account must have read/write on the project, not read-only. If it is currently
read-only, that is one toggle on the Bitwarden project's access page — no value is minted, copied
or pasted.

## Part D — delivery to the router

`platform/llm/external-secret.yaml` today pulls the whole `litellm-upstream` entry from
`estate-vault`. Vendor keys activated through the portal now live in Bitwarden instead, so the
router needs both stores.

External Secrets Operator 2.9.0 supports a per-entry `sourceRef.storeRef`, so this stays one
ExternalSecret and one Kubernetes Secret. Keep the `extract:` of `litellm-upstream` from
`estate-vault` for everything the machine mints, and add one `data:` entry per portal-managed
vendor field with `sourceRef: { storeRef: { kind: ClusterSecretStore, name: human-vault } }`.
A later `data:` entry wins over an earlier `extract:`, which is what makes the portal's value the
one the router uses.

The refresh interval is 10 minutes, which is the number the founder's design named. Reloader
already watches this Secret (`platform/reloader/reloader.yaml`), so LiteLLM restarts when the
value changes and the "written but the pod never picked it up" failure recorded in crew#506 CP4
cannot recur.

Do the same for `platform/prospector/` wherever it reads a vendor key.

## Part E — the watcher

`platform/keywarden/`, delivered as a new row in `clusters/oke/platform.yaml`.

A CronJob on `*/15 * * * *` in the `llm` namespace — not a new namespace, so no new fence is
needed, and the keys it checks are the router's. Copy the shape of
`platform/infra-crew/cronjob.yaml` exactly: `concurrencyPolicy: Forbid`,
`successfulJobsHistoryLimit: 1`, `failedJobsHistoryLimit: 2`, `startingDeadlineSeconds: 600`,
`ttlSecondsAfterFinished: 3600`, `backoffLimit: 0`, `activeDeadlineSeconds: 600`,
`priorityClassName: platform-batch` (so it is seated by preempting a balloon pod and is not
charged against the 6.9-core standing budget), `automountServiceAccountToken: false`,
`restartPolicy: Never`, `runAsNonRoot` with uid/gid 10001 and `seccompProfile: RuntimeDefault`.

Each run:

1. Reads `consoles.yaml` from the same raw URL as Part A.
2. Mounts the `litellm-upstream` Secret as files and, for every vendor row, runs that row's
   `verify:` call with the value it finds.
3. Prints one line per vendor: `ok`, `FAIL <status>` or `absent`. No key value is ever printed.
4. Exits non-zero if any vendor fails.
5. Calls `GET /health` on the router with the master key and prints the count of unhealthy
   deployments, so a lane that is alive only through a fallback is visible. A lane answering 200
   is not evidence that its own vendor is alive: LiteLLM walks `router_settings.fallbacks` and
   sets `x-litellm-attempted-fallbacks` on the response. This is exactly how the DeepSeek and
   `default` lanes were dead without anyone knowing on 2026-09-04.

The alert is the CronJob's own failure, not a new instrument: add a rule to
`platform/monitoring/rules/` firing on `kube_job_failed` for jobs owned by this CronJob, routed
the way the existing rules in that directory are routed. Nothing new to read, nothing new to
watch.

## Part F — rotation

Two cases, decided by the vendor, and the registry says which.

**Vendors with a create-key API.** Add an optional `rotate:` block to a vendor's row in
`consoles.yaml`, in the same shape as `verify:` — `method`, `url`, `headers`, `body`, plus a
`response_key:` JSON path naming where the new key appears in the reply, and a `revoke:` block for
the old one. The warden, when a key is inside 7 days of a known expiry or has failed
verification, calls `rotate:`, proves the returned key with `verify:`, writes it to every entry in
`targets:`, and only then calls `revoke:` on the old one. Order matters: prove, write, then
revoke, so a failure never leaves the estate with no working key.

**No row may be written from a guess.** A `rotate:` block is added only after reading that
vendor's own API documentation, and the row carries a comment naming the page and the date it was
read. A vendor with no create-key API gets no `rotate:` block, and that absence is the signal for
the second case.

**Vendors with no create-key API — DeepSeek today.** The warden cannot mint anything. On a failed
verification it raises the alert from Part E, and the person opens the same portal button from
Part B and pastes the replacement once. That is the assisted case the founder specified, and it is
the whole manual surface that remains in this design.

## Acceptance

The build is done when every one of these passes, with the output shown:

1. `bin/idp-ci` is green, including `shellcheck`, `check-jsonschema` on the gateway config, the
   Backstage entity schema check, and `bin/catalog-refcheck`.
2. `bin/idp-kyverno-render platform/keywarden` renders with no admission refusal — `kustomize
   build` alone does not judge admission policy, and `secrets-not-from-env-vars` has refused
   exactly this shape of workload before (idp#529).
3. In the Backstage backend's tests, `estate:vendor-key:activate` called with a key the vendor
   rejects returns the vendor's status code, and no write is attempted. Assert on the mocked
   Bitwarden client having received nothing.
4. The same action, given a key the vendor accepts, writes one Bitwarden secret per entry in that
   vendor's `targets:` list.
5. No test, log line or error message in the diff contains a key value. `grep -rn` for the shape
   patterns in `consoles.yaml` across the changed files returns nothing.
6. The CronJob's container, run once by hand against the current cluster, prints one line per
   vendor and exits zero when every key is valid.

## What this build does not do

It does not add a second identity layer, a second secret store, a second scheduler or a service
in front of a store. It does not touch the research engine. It does not change how the front door
authenticates anyone, and it does not attempt to close the flat-authorisation gap in
`docs/reference/identity-and-secrets-review.md`, which is a separate piece of work on
oauth2-proxy's `allowed_groups` and each application's role mapping.
