## Part 1 — the four constraints. Each one has already bitten.

1. **The pasted value must never reach a GitHub workflow input.** The 29 existing founder-action
   templates are generated by `bin/idp-portal-buttons` and all use `action: github:actions:dispatch`.
   `workflow_dispatch` inputs are recorded in the run and readable by anyone with repository read.
   This door therefore cannot be a generated button, and `bin/idp-portal-buttons` must not generate it.
2. **The value must never land in a Backstage task log.** The scaffolder records step inputs.
   The value travels as a POST body to a backend endpoint, never as a template parameter.
3. **A zero-knowledge store is written through its own client, never its REST API.** Measured
   2026-09-05T22:08Z: `bws secret create` into the estate project succeeded and was deleted in the
   same run, while the same payload posted at `https://api.bitwarden.com/organizations/<org>/secrets`
   is refused with `400 Key is not a valid encrypted string`. The machine access token
   (`0.<id>.<secret>:<base64 encryption key>`) carries the encryption key, so the vendor client can
   encrypt and the raw API correctly cannot. Road one therefore writes to `estate-vault` **or** to a
   zero-knowledge store the client has issued a write-capable machine token for, and it routes every
   such write through that store's client — for Bitwarden, the `bitwarden-sdk-server` already
   deployed in `external-secrets` for the read path (decision 0020 amendment).
4. **No terminal, no repository secret, no second key while one exists** (LAW 54, LAW 52). The
   founder is customer zero and is graded as a paying client.

## Part 2 — the backend action

New file `backstage/packages/backend/src/credentialIngest.ts`, modelled line for line on
`featureRegister.ts`. Register it at `backstage/packages/backend/src/index.ts` beside
`backend.add(import('./featureRegister'))`.

One endpoint:

```
POST /api/credential-ingest/submit
  { "entry": "cyrus-linear", "key": "api_token", "value": "<pasted>", "store": "estate-vault" }
→ 200 { "entry": "cyrus-linear", "key": "api_token", "sha256_prefix": "9f2c1a7b", "store": "estate-vault" }
→ 400 { "error": "..." }  unknown entry, unknown key, empty value, store not writable
→ 403 { "error": "..." }  caller is not signed in, or entry not in the caller's tenant
```

Rules the implementation must hold, each with a test:

- `value` is read from the body into a local, passed to the vault writer, and dropped. It is
  never logged, never placed in an error message, never returned, never written to disk except
  the temp file `bin/idp-vault-put` already uses and removes.
- The response carries the first 8 hex characters of the SHA-256 of the value and nothing else of
  it, so the person who pasted can confirm they pasted the right thing and no reader learns it.
- `entry` and `key` are matched against an allow-list read at request time from
  `docs/reference/policy/root-trust.md` (rows whose Owner is `Customer`). An entry outside that
  list is a 400. This is what stops the door being a general write primitive into the vault.
- The caller's tenant must own the entry. An operator identity gets no wider allow-list here than
  customer zero does: superadmin is a grant on the operator road and never a widening of the
  customer road (decision 0021 rule 2).
- `store` must be a store with a plaintext write path. Today that is `estate-vault` alone. The
  list comes from a new `platform/vendors/stores.yaml` (part 3), never a hard-coded string.
- The write goes through `bin/idp-vault-put --merge <entry> <key>=<value>` so a vendor key already
  in the same entry is never clobbered, exactly as `bin/idp-estate-seed` does it.
- Every submission emits one span to the central collector (LAW 50) with attributes `entry`,
  `key`, `store`, `sha256_prefix`, `tenant`, and no value.

## Part 3 — the store picker, and what it may offer

New file `platform/vendors/stores.yaml`. One row per secret store the estate can talk to, with
the two capabilities kept separate because they are separate (decision 0020 amendment):

```yaml
stores:
  - name: estate-vault
    label: "The platform's vault"
    provider: oci-vault
    write: true        # a pasted key can land here
    sync: true         # the estate can read from here
    default_for: [Customer, Operator, Supplier]
    why: "Plaintext write path, fine-grained grant per entry, already under the rotation drill."
  - name: human-vault
    label: "My Bitwarden"
    provider: bitwarden-secrets-manager
    write: false
    sync: true
    zero_knowledge: true
    why: >-
      Zero-knowledge: fields are encrypted by the client before they reach the API, so nobody but
      the client can write. Measured by bin/idp-human-vault-probe --write. Keep the key in your
      own vault with your own client and the estate reads it there.
```

The picker renders every row. A row with `write: false` is shown as a *sync source*, with the
`why` sentence in the interface, and its paste field is disabled rather than hidden — a customer
who keeps keys in Bitwarden must be able to see that we support it and understand why we are not
writing into it. Adding a store is a row here, never code (ESO 2.9.0 ships providers for Azure
Key Vault, AWS Secrets Manager, Google Secret Manager, HashiCorp Vault, 1Password, Doppler,
Akeyless, CyberArk and Infisical; each is a `ClusterSecretStore` YAML row).

New template `backstage/templates/onboarding/activate-key/template.yaml`, hand-written, carrying
the comment `# NOT generated: a pasted secret may not travel through a workflow_dispatch input
(spec docs/specs/key-ingest-door.md part 1).` so a future generator run does not eat it.
`bin/idp-portal-buttons` gains a skip for any template carrying that marker, with a fixture pair
proving the skip.

## Part 4 — the grant

The portal's service account gets an OCI vault grant scoped in the shape
`platform/oci/vault.tf:39` already proves, narrowed to the entries whose register Owner is
`Customer`:

```
where target.secret.name in ('cyrus-linear', 'otto-staging-telegram', 'commerce-payment-provider', ...)
```

The list is generated from the register by a small function so it cannot drift, and
`platform/verification/` gains a wall proving the refusal: an attempt by the portal to write an
Operator-owned entry must fail, annotated `estate/expect-ready: "false"` exactly as
`verdict-key-wall.yaml` does. This is the tenant plane failing to reach the control plane, which
is the isolation leak decision 0021 exists to catch.

## Part 5 — acceptance

Done is these commands, in this order, with this output:

```
bin/idp-human-vault-probe --write            # PASS: reads work, plaintext write refused
yarn --cwd backstage test credentialIngest   # value never logged, sha only, allow-list enforced
bin/idp-ci                                   # portal-app green, new fixture pair both ways
```

Then the end-to-end, which is the only proof that counts (THE EMPIRICAL PROOF RULE):

1. Sign in to the portal as customer zero. Open **Activate a key**. Choose the Linear entry.
   Paste the key. Submit.
2. The page shows the sha prefix. No terminal was opened, no name was typed into any vendor's
   web interface, no repository secret was created.
3. Within one refresh interval:
   ```
   bin/idp-kube get externalsecret cyrus-webhook -n cyrus -o jsonpath='{.status.conditions[0].reason}'
   → SecretSynced
   ```
4. Quote a real line from `bin/idp-kube logs -n cyrus deploy/cyrus --tail=100` showing a Linear
   webhook delivery verified and acted on. Until that line exists the door is not working.
5. `bin/idp-root-trust` prints a lower onboarding number than the four it prints today.

## Part 6 — the first customer, and the debt it pays

The door's first user is the credential that is down right now. `cyrus-linear-api-token` has been
handed over by hand three times on 2026-09-05 and landed nowhere: the estate's Bitwarden project
holds zero secrets and the machine account reads it correctly, so every failure was the interface,
not the permission. That is the friction this spec removes, and the register's onboarding line is
how we will know it stayed removed.
