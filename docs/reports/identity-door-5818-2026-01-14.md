## CSP Fix — Safari iOS "not allowed by CSP" (2026-10-18)

**Root cause found and fixed.** The passkey sign-on rule (`39b58988d9784298a6d76afd53deb934`, created 2026-10-13 by `estate-ci`) carried a circular condition:

```
attributeName: subject.authenticatedBy
operator: in
attributeValue: ["FIDO_AUTHENTICATOR"]
```

Read literally: "was already authenticated by FIDO_AUTHENTICATOR" — impossible on a first sign-in, before any authentication has happened. The script's own comment called it "signed in BY the FIDO authenticator", confirming the condition was backwards from the start.

Yet the rule somehow matched in Safari iOS, triggering IDCS's WebAuthn ceremony from a path that Safari blocks with `NotAllowedError: not allowed by CSP`. Face ID was always working through the **2FA rule** (`authenticationFactor: IDP+2FA`, `2FAFactors: FIDO_AUTHENTICATOR`) — the drill proves it. The passkey rule was dead code that happened to cause a browser-specific failure.

**Fix applied (live, 2026-10-18):**
- Policy updated: passkey rule removed from "Front Door Sign-On Policy" — now one rule, sequence 1, the 2FA rule
- Passkey rule deleted from the domain (rule `39b58988d9784298a6d76afd53deb934`, 204 No Content)
- `bin/idp-identity-apply` updated: `pk_want=false` hard-off, passkey rule creation block replaced with a no-op, never recreates the broken rule on next apply run
- Policy description updated

**Probe after fix:**
```
{"policy":"Front Door Sign-On Policy","called":[{"rule":"64497e596bfc490fbf5d27a6c46279e5","sequence":1}]}
```

Face ID works through the 2FA path. The IdP policy (`front door identity providers (everyone)`) still adds `FIDO_AUTHENTICATOR` to the sign-in form's LocalIDPs — that is where the factor appears, and it is unaffected by this change.

The correct path to Face ID alone (no password, no second factor) requires a different condition vocabulary — `user.groups` scoped to the pilot cohort, not `subject.authenticatedBy`. That is the next door (#5878).
