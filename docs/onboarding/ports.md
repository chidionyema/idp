# Onboarding: ports

## The rule
The catalog is the port registry. Every TCP port anything on the machine listens on is a
`Resource` of type `port` in `catalog/catalog-info.yaml`, with its owner (the container that
published it, or the process), and `catalog/ports.md` is the same rows as a table. Both are
generated by `bin/catalog-gen` from the LAW 39 inventory (`~/.estate/scripts/inventory.py`,
`discover_listeners`), which reads the process table. Nothing is hand-edited, so the ledger cannot
say one thing while the machine does another.

`bin/idp-ci` refuses an inventory in which two things claim one port (`ports` row), and the
inventory's `findings.port_collisions` names them.

## Claim a port
1. Read `catalog/ports.md`. Pick a free port in the block for the surface:
   3000–3099 product web, 3100–3199 product APIs, 3200–3299 platform UIs (Langfuse 3200,
   Dagster 3210, Kanboard 3300 is a grandfathered exception), 4000–4099 model routing (LiteLLM
   4000), 4300–4399 telemetry (OTel 4318), 8000–8099 monitors (Healthchecks 8000), 8700–8799 agents.
2. Bind it in the compose file or service config with a comment naming the block.
3. Run the inventory and `bin/catalog-gen`; commit `catalog/catalog-info.yaml` and `catalog/ports.md`.
   A collision stops the generator and CI.

## Why not a hand-written PORTS.md
It was proposed on 2026-08-24. A ledger a person maintains drifts the first time someone binds a
port at 2am to get a UI up — which is exactly how Dagster landed on 3210 undocumented. The
generated ledger is measured, and the guard runs in CI.
