One bound, at the door

Three numbers were bounding the same work. Two of them could never fire, and the third reported a failure that had not happened. This is what changed, why each bound was judged separately, and the gate that now refuses a second one.

01 The defect

A step in an intent is a shell command. Its wall-clock time was decided in three places, and none of the three knew what the others said:

WhereThe numberWhat it actually did
mcp/plugins/estate_executor.py 100s binds the only number that kills a job
platform/estate/bin/estate-execute 120s inert a per-step default above the ceiling, so it could never fire
mcp/plugins/estate_mcp.py 55s inert a second opinion 45s below the door
platform/estate/intents/*.yaml 24 lines guesses step caps and timeout N inside commands

A 120s default against a 100s door is not a safety margin, it is a comment. It made the number that actually kills the job invisible in the script's own story: read estate-execute and you would conclude nothing kills a step before two minutes.

Two failures, both measured

2026-10-22 — the push that was told it had failed. lane-submit ran its push behind timeout 50 inside a 60s step. The push took longer, the step was killed at 60036ms, and git ls-remote then reported the lane ref absent — so the estate was told the submission had failed while the push was still landing.

2026-10-25 — the same fix, applied twice. The bound was raised to timeout 80 inside a 100s step. The same push, with the estate's pre-push guard attached, took 98s. Same false failure, one number larger.

real 1m38.120s · fast-gate green · jev advisory · then the push itself

A guessed bound cannot be right more often than the distribution it guesses about, and where it is wrong it is wrong in one direction only: it invents a failure. Raising the number is not a fix — it is the same fix applied twice.

02 The rule

Wall-clock time is bounded once, at the door. An intent declares a budget; a step may narrow it, never widen it; nothing else may carry a bound of its own.

  1. door_s: is the intent's budget, in seconds. Absent, it is the ceiling — imported from the module that defines it, never restated.
  2. A step may set timeout: below the budget and never above. Wider is printed as INERT BOUND and clamped; a non-integer is refused with rc=2. The error names the budget and its source.
  3. A bound inside a step command is refused outright. A step cap is legal only where it splits one budget between sequential jobs.
  4. A probe may be bounded shorter than the work it guards — a hung probe has to fail, not hang the step — and must say why: timeout 2 curl -sf …/health # estate:bound the service must fail fast. A marker with no reason is a rubber stamp, and the gate refuses it.
  5. If the work needs longer than the door allows, the answer is the session plane, not a larger literal.

03 The eradication, bound by bound

This was not a blanket strip. Each of the 25 step bounds was read and judged: delete it, split the budget with it, or keep it as a marked probe.

What replaced the guess in lane-submit

The old bound existed to guarantee one thing: that after the push, the estate re-read the remote ref before deciding. That guarantee does not need a wall clock — it needs a re-read. The step now re-reads origin's ref endpoint up to five times after the push exits, and when the push outlives the window it says IN-FLIGHT with the pid and the verdict command. It never says absent when it means unknown.

04 The library that actually runs

Reviewing the checkout is not enough. ~/.estate/intents — the directory every agent invokes — is main's 96 intents plus ~266 crystallized on this laptop that exist nowhere else, and estate-runtime-sync only ever adds or updates it. It never deletes. Measured 2026-10-25, before the eradication:

A gate that graded only the checkout would have called this estate clean while every agent on the machine ran inside a guess.

05 The gate

bin/timeout-budget is rung 1f of bin/idp-ci. It fails on:

  • a door_s above the ceiling — time no door grants;
  • steps whose declared caps sum past the budget;
  • a step cap wider than the budget;
  • a literal wall-clock bound inside an intent command (strict);
  • a new literal bound in bin/ or hooks/;
  • any of the above in ~/.estate/intents, the library an agent actually invokes.

It shipped as a ratchet, not a wall: twelve bounds were already in bin/ when the gate was switched on and went into bin/timeout-budget.baseline, because a strict gate would be red before any lane touched anything, and a gate every lane must bypass is not a gate. That baseline may only shrink — and in the same lane it went to empty, bound by bound rather than stripped:

So --strict-ratchet is green, and every surviving number in the tree is either the door's own or a probe with a written reason. The gate is rung 1f of bin/idp-ci.

The gate is graded the way it grades a bound — by being run against a tree it must refuse. Its own suite covers a step cap wider than its budget, a door above the ceiling, steps summing past one door, a literal bound inside a command, a marker with no reason, and a second identical bound slipping past the first one's baseline entry. Twelve tests, all of which run the real script against a real checkout.

06 How to check any of this

bin/timeout-budget --no-installed # the checkout alone, for a machine with no runtime library
bin/idp-ci # rung 1f of the offline gate
python -m pytest tests/test_timeout_budget.py tests/test_lane_submit_fits_the_door.py

The doctrine — the decisions, the numbers, and the two measured failures — is docs/decisions/0043-the-bound-lives-at-the-door.md. The reason it is a decision record and not a paragraph in a commit message: the estate has now shipped the same guess twice, and a number that is only in a commit message is a number nobody can contradict.
