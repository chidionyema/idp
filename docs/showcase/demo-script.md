# Demo script — what to say when the buyer is in the room

A line-by-line script for the three stages of the buyer journey. Read
the page alongside the
[`install-wedge.md`](./install-wedge.md) narrative and the
[`docs/runbooks/demo-sandbox.md`](../runbooks/demo-sandbox.md) runbook.

## Stage 1 — the 30-second hook (one screen, no clicks)

The buyer has just opened `/showcase`. While they look at the page,
say:

> "What you are looking at is the platform's audit of itself. The
> bar at the top is `ELITE / GAP / BLIND` across every entity we
> catalogue; the standards table below it names the rows of
> `crew/docs/STANDARDS.md` we have already adopted. The five tiles
> under 'What Otto does today' are the Otto capabilities currently
> marked LIVE in
> [`docs/specs/otto-capability-inventory.md`](../specs/otto-capability-inventory.md)
> — every tile names the proof file you can open. The numbers come
> from the on-disk `docs/SHOWCASE.md`, regenerated by
> `bin/estate-showcase`; the `--check` flag fails when the page goes
> stale."

Pause for the buyer's engineer to open the audit page source. They
should land on a single YAML front matter that names the inventory
timestamp.

Then point at the button.

> "This button is the wedge. Press it, pick a hold, and a sandbox
> cluster appears inside the existing cluster within two minutes. It
> expires on its own. A person presses it; an agent cannot."

## Stage 2 — the 5-minute self-prove (terminal open, three commands)

After the buyer presses the button, open a terminal. While the
Kustomization reconciles, say:

> "The button wrote a branch called `sandbox/launch` and the cluster
> is already reading it. The reconciliation is the same Flux path
> every other Kustomization on the cluster uses — there is no second
> install path, no hand-built demo environment that drifts from
> production."

When the run reports ready, show the buyer:

```sh
flux get sources git -n flux-system sandbox-launch
flux get kustomizations -n flux-system demo-sandbox
kubectl -n demo-sandbox get pods
```

> "Three lines. Source `Ready True`. Row `Ready True`. One pod
> `Running`. The shop page answers at `https://sandbox.<zone>`
> through the shared edge. Hand the buyer's engineer a `vcluster
> connect demo-sandbox -n demo-sandbox` line and they have a full
> cluster of their own — list, deploy, break, restore."

While the buyer explores, point out:

> "The pod has a `cleanup.kyverno.io/ttl` label and a creation
> timestamp. The countdown on the portal reads them through the same
> Kubernetes proxy the audit bar reads. Watch the bar shrink in real
> time; when the timer hits zero, the fifteen-minute sweep empties
> the branch and Flux prune removes everything the row created."

## Stage 3 — the 30-minute deep dive (artefacts open)

The buyer is staying for the diligence. Open three artefacts in
parallel:

1. The runbook itself: [`docs/runbooks/demo-sandbox.md`](../runbooks/demo-sandbox.md).
   > "Every bound I just said is pinned in a single test:
   > `tests/test_demo_sandbox_is_defined_and_expires.py`. Open it,
   > read the assertions, run `pytest` on it — it is the diligence
   > artefact."
2. The audit page freshness check:
   > "`bin/estate-showcase --check` exits `0` when the audit page
   > matches the catalogue. A red exit is a failing freshness gate;
   > we run it on every change."
3. The rule chain:
   > "`bin/idp-ci` runs the rules in `rules.yaml` — the namespace
   > fence, the static-secret gate, the JIT grant catalogue, the
   > scheduler coverage. A pull request that lands with a red rule
   > does not merge."

While the buyer is reading, take one question: "What about agents?"
Answer:

> "The runbook's `agents never deploy` line is unchanged. The button
> is a person's button; the press writes a branch, the cluster reads
> it. An agent with cluster access can read state through the proxy
> `useEstate.ts` exposes, but it cannot launch or end the sandbox."

## Stage 4 — the question that ends the demo

Almost every buyer asks one of three questions. Pre-answer them.

- **"How is this different from a stock Backstage?"**
  > "The catalogue is the asset; the portal is a renderer. A second
  > renderer (Datasette, on a different runtime) renders the same
  > inventory. The audit bar, the standards table, the countdown —
  > every figure on `/showcase` is read from the catalogue or from
  > the cluster, not retyped."
- **"What does the buyer own?"**
  > "The catalogue, the decisions, the rules, the inventory. The
  > estate ships one row per layer on the standards page
  > (`crew/docs/STANDARDS.md`); a row that is `live` is one we run
  > ourselves; a row that is `to adopt` is one we will run when the
  > criteria are met. The 25 ADRs in [`docs/decisions/`](../decisions/)
  > are the architecture."
- **"Where is the receipt?"**
  > "Every drill is a workflow that proves a wall is a wall. The
  > `bin/idp-drills` runner records verdicts in the collector; the
  > `login-drill.yml` workflow captures screenshots of `/showcase`,
  > `/tools`, and `/ops` every hour on the hour. The screenshot is
  > the case study."
