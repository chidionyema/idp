# The install wedge — what a buyer's engineer does in the first hour

> A buyer's engineer opens this page when they want to see the platform
> actually running on their own cluster. The drill below is the demo;
> the runbook is the case study.

This page is the buyer-facing narrative for the existing install path.
The platform's one install wedge is the **buyer sandbox** described in
[`docs/runbooks/demo-sandbox.md`](../runbooks/demo-sandbox.md) — a
cluster-in-a-cluster a buyer's engineer holds for one hour or four,
expires on its own, and leaves nothing behind. There is no second
install wedge: the HEADLINE rule binds the layers underneath to one
implementation each, and the buyer's first hour rides the same Flux
path the estate runs in production.

## What the buyer proves in 60 seconds

- **The portal renders the live audit bar.** `/showcase` on the estate
  shows `ELITE / GAP / BLIND` entity counts and the standards table
  from the on-disk `docs/SHOWCASE.md` (regenerated by `bin/estate-showcase`).
  The numbers are live, not screenshots.
- **The five LIVE Otto capabilities are visible.** Read from
  `docs/specs/otto-capability-inventory.md` itself; one row per
  capability with its proof file.
- **The buyer's first action is one button.** `Launch the buyer sandbox`
  on the portal runs the canonical `flux create kustomization demo-sandbox`
  command the runbook already documents. A person presses it; the
  button does not let an agent press it ("agents never deploy").

## What the buyer does in 5 minutes

1. **Launch the sandbox.** Portal → founder actions → *Launch the buyer
   sandbox* → pick `1h` or `4h`. The run lands under
   `https://github.com/chidionyema/idp/actions/workflows/demo-sandbox.yml`.
2. **Watch it come up.** Within about two minutes:
   ```sh
   flux get sources git -n flux-system sandbox-launch   # Ready True
   flux get kustomizations -n flux-system demo-sandbox # Ready True
   kubectl -n demo-sandbox get pods                    # demo-sandbox-0 Running
   ```
3. **Open the shop.** The seeded demo shop answers at
   `https://sandbox.<zone>` through the shared edge (the
   `https-sandbox` listener on the prospector edge gateway). The buyer
   pokes anything they like: list, deploy, break things. Nothing in
   here touches the real cluster.

## What the buyer proves in 30 minutes

- **Bounded, catalogued, mortal.** The Kustomization carries a
  `cleanup.kyverno.io/ttl` label and a creation timestamp; the
  countdown reads them through the same Kubernetes proxy `useEstate.ts`
  already uses. The buyer sees the bar shrink in real time.
- **The expiry runs itself.** Nothing to remember, no follow-up. The
  fifteen-minute sweep empties the branch, Flux prune removes what the
  row created, the area costs nothing between runs.
- **Ask Investigate anything.** The Holmes chat (`/investigate` →
  `/holmes` proxy) answers questions about the sandbox without shell
  or internet access; it's a read-only investigator.
- **Diligence artefacts are on disk.** `bin/estate-showcase --check`
  exits 0 when the audit page is fresh; `bin/idp-ci` runs the rule
  chain; `tests/test_demo_sandbox_is_defined_and_expires.py` pins the
  open-source image, the processor ceiling, the no-storage rule, the
  standing area, the front door, the button choices, and the sweep.

## What this page deliberately does not promise

- **There is no `idp/quickstart` Docker image.** The marketing
  catalogue uses that phrase as a working name for "the install wedge",
  but the implementation is the Flux-based sandbox above. Bundling the
  whole platform into a single container image would be the
  "stitched-together solution" the platform's HEADLINE rule forbids
  (one platform layer per row, no second copies).
- **The buyer's first hour runs on the buyer's existing cluster.**
  The wedge is a Kustomization row, not a new container. If the buyer
  does not have a cluster, the runbook points at `docs/specs/kini-master-spec.md`
  for the A1-4-16 / A1-6-24 node floors the `bin/idp-features plan`
  calculator sizes for.

## Where the guarantees live

| Bound | Where it is pinned |
|---|---|
| Open-source vCluster image | `tests/test_demo_sandbox_is_defined_and_expires.py` |
| Quarter-core processor ceiling | same test |
| No persistent storage on the sandbox row | same test |
| Standing area + front door | `platform/sandbox/launch/` (Flux sources) |
| The portal button's choices (`1h`, `4h`) | `backstage/templates/founder-actions/demo-sandbox/template.yaml` |
| The fifteen-minute sweep | `.github/workflows/demo-sandbox.yml` |
| The countdown reads through the same proxy as `/showcase` | `backstage/packages/app/src/modules/home/useEstate.ts` (existing) |

## FOUNDER ACTION

A buyer asking for a *single self-contained image* (`idp/quickstart`
Docker image, k3d bundled) is asking for the thing THE HEADLINE rule
forbids. Filing this so the founder sees the request and decides
whether the rule bends for this use case. If the answer is yes, this
page becomes a one-line wrapper around the new image and the
guarantees table above moves into the Dockerfile.
