# The one-hour buyer sandbox, step by step

A throwaway cluster-in-a-cluster a buyer's engineer can hold for one hour or four. It runs
inside the existing cluster, its control plane may not ask for more than a quarter of one
processor core, and it deletes itself on schedule. No cleanup step, no follow-up, nothing
to remember.

## What launches, and what expires

The founder presses **Launch the buyer sandbox** on the portal
(`backstage/templates/founder-actions/demo-sandbox/template.yaml`, generated by
`bin/idp-portal-buttons`). That one press runs `.github/workflows/demo-sandbox.yml`, which
writes a branch called `sandbox/launch`: one Flux row named `demo-sandbox` pointing at
`platform/sandbox/vcluster`, plus a ConfigMap the portal's Showcase page reads for the
hold and the expiry. Nothing in continuous integration holds a cluster credential — the
workflow writes a branch, and `clusters/oke/sandbox.yaml` makes the cluster read it
(`platform/sandbox/launch`): the sandbox appears on the cluster within about two minutes
of the press, and the shop answers at `sandbox.<zone>`.

That folder holds the sandbox control plane (vCluster, the open-source build, pinned) and
a small demo shop seeded inside it, dated with the hold the founder chose. The branch is
the clock: the same workflow runs every fifteen minutes, reads the expiry off the branch,
and once the hold has run out it rewrites the branch without the Flux row. Flux prune then
removes everything the row created. What a sandbox needs before it exists — its area of the
cluster and its front door at `sandbox.<zone>` — is not the row's to create or remove: both
stand in the launch lane (`platform/sandbox/launch`), so the certificate and the address
never wait on the thing they let in. Empty, the area costs nothing between runs.

## Launch (a person presses this; agents never deploy)

Portal → founder actions → **Launch the buyer sandbox** → pick *Launch a sandbox* and a
hold of `1h` or `4h`. The run lands under
<https://github.com/chidionyema/idp/actions/workflows/demo-sandbox.yml>.

## Verify it is up

```sh
flux get sources git -n flux-system sandbox-launch
flux get kustomizations -n flux-system demo-sandbox
kubectl -n demo-sandbox get pods
```

Expect the source `Ready True`, the row `Ready True`, and one running pod named
`demo-sandbox-0` within about two minutes. The shop page answers at
`https://sandbox.<zone>` through the shared edge (the `https-sandbox` listener on the
prospector edge gateway). To hand the buyer's engineer a way into the cluster itself, the
vendor's client tool connects with:

```sh
vcluster connect demo-sandbox -n demo-sandbox
```

## Expiry, and ending it early

Nothing to do: the hold elapses, the next fifteen-minute sweep empties the branch, Flux
prunes the sandbox. To end it early, press the same button with *End the one that is
running* — the branch is emptied on the spot and the sweep confirms it.

## Where the guarantees live

Every bound above is pinned by `tests/test_demo_sandbox_is_defined_and_expires.py`: the
open-source image, the processor ceiling, the no-storage rule, the standing area and front
door, the button's choices, the fifteen-minute sweep, and the portal button generated from
the workflow itself.
