# Runbook: a new site or backend API

Founder, 2026-10-18, after meridian: *"we need a parameterized intent to deploy a new website or
backend API."* Meridian's application was written once; standing it up took **four** merged fixes
afterwards, and not one was a bug in the application. Each was a declaration missing from a
*different* shared file, and each failed somewhere that named something else:

| Fix | The declaration that was missing | What the founder would have seen |
|-----|----------------------------------|----------------------------------|
| #6503 | the Gateway listener that claims the hostname (`platform/edge/prospector-gateway.yaml`) | the route is Accepted, the Service answers 200 inside the namespace, the public name is a Traefik **404** |
| #6511 | `egress_internet: [80, 443]` for cert-manager | the certificate stays `RequestChanged`; HTTPS cannot be trusted |
| #6513 | `flows.edge.egress` naming the new namespace | the request **hangs after a completed TLS handshake** -- Traefik's SYN is dropped, so nothing sends a reset and nothing returns 502 |
| #6518 | `ingress_from: [edge]` on cert-manager | every HTTP-01 challenge times out with `context deadline exceeded` while the same URL answers 200 from the node |

All four are derivable from a name and a hostname. `site-onboard` derives them.

## The three commands

```bash
# what would change -- writes nothing, prints every CREATE and EDIT
estate-execute site-onboard name=pulsera hostname=pulsera

# write it into the worktree, then regenerate the fences from allowances.yaml
estate-execute site-onboard mode=write name=pulsera hostname=pulsera

# the gate: one line per declaration, exit 1 for each one missing
estate-execute site-onboard mode=verify name=pulsera
```

`hostname` is the **label only** -- `${ESTATE_ZONE}` is appended, because
`bin/estate-zone-gate` refuses a literal hostname in the tree (the zone moves with the estate).
Omit `hostname` for something internal: no listener, no allowance, no public name.

Useful parameters: `kind=api` (probe on `/healthz` instead of `/`), `port=`, `replicas=`,
`tier=internal` (allows one replica), `secret_entry=<vault entry>` (mounts it optionally),
`runtime=scale-to-zero`.

## What it writes

Nine files, and five declarations inside shared files:

```
platform/<name>/namespace.yaml        restricted, prune-disabled, edge-attach
platform/<name>/deployment.yaml       Service + Deployment (2 replicas, spread, probes, pull secret)
platform/<name>/pull-secret.yaml      ghcr-pull from the cluster store -- no laptop needed to pull
platform/<name>/public-door.yaml      HTTPRoute on <name>.${ESTATE_ZONE}
platform/<name>/vault-secret.yaml     only with secret_entry
platform/<name>/kustomization.yaml    $imagepolicy marker: the tag is Flux's, never typed
clusters/oke/<name>.yaml              the Flux row (zone substituted from estate-config)
platform/image-automation/<name>.yaml ImageRepository + ImagePolicy
backstage/platform/catalog-info.yaml  the catalogue entity (require-catalogue-entity is Enforce)

platform/edge/prospector-gateway.yaml  + listener https-<name> on the shared certificate
platform/ns-fences/allowances.yaml     + flows.edge.egress AND flows.<name>.ingress_from
platform/ns-fences/network/            + both regenerated by bin/idp-ns-fence-gen
clusters/oke/kustomization.yaml        + the row (an unlisted file is silently not applied)
platform/image-automation/kustomization.yaml  + the row
```

The edits are textual and anchored on purpose: a YAML round-trip would delete the comments that
record which outage produced each line, and `platform/ns-fences/allowances.yaml`'s comments are
that record. A plan that would produce invalid or ambiguous YAML is refused before anything is
written; a second write changes nothing.

## Then

1. `mode=verify` green: every declaration present, in the tree.
2. Commit with the claim's trailers, then `estate-execute lane-submit`. **Never** `gh pr create` and
   never push main -- the Greenlane raises the pull request and lands it (AGENTS.md 2).
3. The image: `build-multiarch` finds `web/<name>.Dockerfile` by itself. Until the first image is
   pushed the Deployment sits in `ImagePullBackOff` on `main-0-bootstrap`, which is the honest
   bootstrap state.
4. **Done is a production log line**, not a green lane: `https://<name>.${ESTATE_ZONE}` answering,
   with a request in the pod's log.

## What it does not do

- **The application**: repo, Dockerfile, tests, CI and scanners are the Backstage golden path
  (`docs/specs/self-service-golden-paths.md`). This is the platform half of the same ask.
- **The DNS record**: external-dns writes it from the HTTPRoute hostname once the route exists.
- **The certificate**: cert-manager re-issues the shared certificate to include the new hostname
  because the listener names it -- that is why the listener is added, not just the route.
- **The vault entry**: it names `secret_entry` and mounts it optionally. Until the entry exists,
  the site serves and any endpoint that needs it answers 503 rather than accepting work it would
  drop. Creating the entry is a founder/vault action (`estate-secrets`).
- **The cluster**: Flux is the only writer.

## A contact form that delivers to Telegram

`web/lib/contact.ts` is the reusable piece for any site whose form should reach the founder. It
reads two named secrets (env first, then the file mounted from the vault entry) and sends a
plain-text `sendMessage`: `TELEGRAM_BOT_TOKEN` and `TELEGRAM_CHAT_ID`. A generic
`CONTACT_WEBHOOK_URL` (+ `CONTACT_WEBHOOK_TOKEN`) still works and wins when set. With neither, the
route answers 503 `delivery_not_configured` instead of accepting a lead it would drop.

For a new site, pass `secret_entry=<name>` to `site-onboard` and seed the vault entry with the
properties `bot_token` and `chat_id`; meridian's `platform/meridian/deployment.yaml` shows the
ExternalSecret template that maps them to the two file names. A namespace with its own fence also
needs `egress_internet: [443]` to reach `api.telegram.org`; meridian has no fence of its own.

## If the certificate is the thing that is stuck

`mode=verify` grades the tree, not the cluster. When the tree is green and the padlock is not, the
question is whether the controller can reach itself: cert-manager needs `egress_internet: [80, 443]`
(#6511) *and* `ingress_from: [edge]` (#6518), and the new namespace needs both halves of its edge
allowance (#6513). All three are checked by the gate; a live challenge that still times out is a
cluster question, not a declaration question.
